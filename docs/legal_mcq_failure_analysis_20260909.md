# LegalMCQ 30 题失败归因报告

## 1. 结论与证据范围

本次主要问题不是已经证明“美团模型不会做法律题”，而是当前三角色工程链路
无法稳定取得可用输出：30 题中 22 题以异常结束，只有 8 题返回答案。
模型输出协议、响应适配、重试预算、时间控制、题干解析和核验契约都有问题。

本报告依据：

- `output/legal_mcq/lexgenius-30-20260908-seed42/results.jsonl`；
- 同目录的 `results.summary.json`、`config.yaml` 和 `manifest.json`；
- 与 manifest 哈希一致的运行源码；
- 无外部网络的合成响应、MockTransport 和 Fake Model 复现；
- 先前 smoke test 留存的少量响应，仅作为辅助证据；
- 对唯一答案标签冲突题进行的最高人民法院公开法条核查。

本次分析没有重新请求付费模型，没有修改实验配置、源码、数据标签或原结果。
30 个 dataset_index 为连续的 0 至 29，题目 ID 无重复；文件已全部保存。
数据、配置、运行源码哈希与启动时一致，因此不能把这些失败归因于用户最后的中断。

## 4. 输出协议与响应适配

### 4.1 全局 token 预算与单次生成上限不是一回事

本次全局预算是 32768，但单次上限仍是：

- Controller：1200；
- Solver 和 Solver Revision：2400；
- Verifier：768。

`agent.py:171` 使用 `min(config.max_tokens, max_tokens)`，而上述数字还写在
各角色调用点。因此，仅提高 YAML 里的角色 max_tokens 或总预算，未必增加
真正传给模型的生成上限。

Solver 同时输出争点分析、所有选项、原子命题、理由、规则、置信度和总解释。
已有成功响应在压缩 JSON 后仍有 1799 至 3607 个字符；还有重复题目上下文、
Controller 结构和修订意见。字符数不是模型 token 数，不能据此断定截断，
但该协议没有限制解释长度，生成长度与预算不匹配是需要验证的风险。

请求只发送普通 Chat Completions 参数，没有 `response_format`、JSON Schema
约束或 reasoning 控制字段。模型必须仅靠提示词遵循复杂协议；供应商是否
支持这些结构化能力，需要在后续适配时确认，不能假定支持。

### 4.2 已复现：空正文可被误解释为“缺少选项”

`model.py:80-105` 的行为：

1. `message.content` 是字符串时返回字符串。
2. 如果 content 为 null 且消息有 `model_dump()`，则序列化整个消息对象。
3. `SolverDecision.from_text()` 接收到包含 role/content 等元数据的 JSON。
4. 该对象没有 `selected_options`，于是报告 `selected_options cannot be empty`。

用真实 OpenAI SDK 的 ChatCompletionMessage 构造
`content=None, finish_reason=length` 的合成响应，可以复现完全相同的错误。
这证明代码存在适配缺陷，但不能证明本批次 5 个同名错误全部来自这一原因。
`selected_options` 字段确实缺失、字段名错误、对象为 `{}` 或数组为空也会触发它。

因此，之前根据这个错误断言“模型没有给出答案”或“全用于隐藏推理”证据不足。

### 4.3 缺少能够判定截断的元数据

`ModelResponse` 和 `OpenAIChatModel` 不保留：

- `finish_reason`；
- `completion_tokens_details.reasoning_tokens`；
- refusal 信息；
- 上游实际返回的模型标识；
- content 是否为 null，与空字符串的区别。

合法 JSON 代码围栏本来已经被 `extract_json_object()` 支持。
`malformed Markdown JSON fence` 既可能是截断，也可能是围栏后的解释、
不符合正则格式的围栏等情况，不能自动等价为“没有闭合”。

先前 smoke 中确实留有一个空 Solver 正文文件，但那次 Solver 是
DeepSeek，不是本批次的 LongCat；它不能代替本批次原始响应证据。

### 4.4 重试方式没有针对失败原因

当前对解析失败采取同一个动作：将上一响应加入上下文，再要求完整重写 JSON。
没有区分缺失字段、拒答、空正文、截断、供应商错误，也没有针对长度风险缩短
解释或修复具体字段。第二次仍使用相同输出上限，却携带更长输入。

这会放大 token、延迟和调用预算消耗，但本批次没有保存每次响应，
无法精确分解每题的重试原因与耗费。

## 5. 调用预算与修订链路冲突

正常流程需要 3 次逻辑模型调用：

```text
Controller -> Solver -> Verifier
```

发生业务修订需要 5 次：

```text
Controller -> Solver -> Verifier -> Solver Revision -> Verifier 2
```

但 schema 重试也使用这同一个 5 次预算。只要前面多发生一次重试，完整链路
就变成 6 次。配置层只检查 `3 + 2 * max_revision_rounds`，没有为这种情况
预留收尾调用；编排层也没有在启动修订前检查能否完成后续核验。

离线复现结果：

```text
Controller
Solver（无效 JSON）
Solver（有效）
Verifier（要求修订）
Solver Revision（有效）
Verifier 2（被 max_calls 阻断）
```

实际调用计数：Controller 1、Solver 3、Verifier 1；第二轮 Verifier 被阻断，
整个题目抛异常。即使已经得到一个可用候选，当前也没有保留该候选的 partial
结果出口。

这解释了预算冲突的确定性机制。本批次 3 题确实触发 `max_calls`，
但未保存其完整 Trace，不能逐题证明都走了上述同一顺序。

改进方向不是无条件扩大调用数，而是预算感知的编排：先保留最后一次核验的
配额，确定足够再开始修订；不足时明确记录未核验候选或 partial，
不能把未核验结果伪装成 completed。

## 6. 180 秒不是端到端硬超时

5 个时间预算失败的单题耗时分别为：

| 题目 ID | 秒 |
|---|---:|
| 6 | 337.37 |
| 9 | 349.81 |
| 17 | 455.06 |
| 19 | 309.09 |
| 29 | 213.91 |

还有 ID 11 在 188.33 秒后以 schema error 结束。

代码原因：

- `ExecutionBudget.reserve()` 仅在准备发起下一次逻辑调用时检查 elapsed。
- 进行中的请求没有被题级 deadline 取消。
- `settle()` 检查 token，但不检查墙钟超限。
- `build_openai_role_clients()` 使用每请求 timeout=60、SDK max_retries=2，
  没有把题目剩余时间传到网络层。
- SDK 超时与重试也不等价于完整工作流硬 deadline。

离线假时钟复现：第一调用经过 240 秒仍返回成功，下一调用才触发
`max_seconds`。所以“预算配置为 180 秒”不代表每题一定在 180 秒内结束。

另外，使用 httpx.MockTransport 连续返回两次 500 再成功，证实：

```text
实际 HTTP 尝试：3
ExecutionBudget.calls_used：1
```

5 次是逻辑调用上限，不是严格 5 次供应商 HTTP 尝试。
这会放大延迟并削弱费用观测；并不意味着本批次每次调用都实际发生了 SDK 重试。

## 7. 已确认的输入解析缺陷

### 7.1 案情里的否定词污染了提问极性

`parser.py:23-25,145-149` 对整段 stem 搜索“错误”“不符合”等词。
法律题 stem 包含案情和问题，不是只有最后的提问。

| ID | 案情中的命中词 | 实际提问 | 当前解析 |
|---|---|---|---|
| 5 | 不符合破产条件 | 不予受理主要基于哪项法理冲突 | 选错误项 |
| 12 | 分别罚款错误 | 法官应如何解决法律与道德冲突 | 选错误项 |
| 25 | 逮捕错误 | 哪项制度创新最能防止权力滥用 | 选错误项 |

这三个例子可直接用本次数据离线复现。
错误 metadata 会送给模型，并使 DecisionValidator 使用 contradicted
作为选择目标。即使 Solver 按题意正确作答，也可能被代码否决或要求修订。

ID 5、12 最后表现为 Solver schema error，ID 25 是 max_calls。
极性错误是这些样本的已确认输入缺陷，但不能在缺失逐调用记录的情况下
断言它直接造成了每个最终异常。

### 7.2 首个日期不一定是法律适用日期

ID 20 背景讲述历史案件，问题明确提出“若本案发生在2023年”。
解析器优先取首个完整日期，最终输出 `1997-06-23`。

应区分案发日期、裁判日期、法源版本和题目假设时间；遇到多个时间锚点时，
不应简单把第一个日期强制设置为适用法日期。

## 8. Controller 和 Verifier 并非完全规范

### 8.1 Controller 的中立性只检查字段名

Controller 禁止 `answer`、`selected_options` 等字段，但自然语言可以
在 `trap_checks`、`option_claims` 中提前表达结论。

ID 13 中已经出现：

> 将“当事人同意原则”绝对化为“一票否决权”的逻辑陷阱

以及：

> C2: 混合开庭模式不违反在线诉讼程序的基本规则

这些内容通过了 Controller schema 校验，随后进入 Solver 与 Verifier 上下文。
这证明“字段中立”不等于“语义中立”，但不能据此证明 Controller 对最终答案
产生了因果影响，或证明该法律结论错误。

Controller 和 Verifier 又使用同一种 Qwen 模型，后者看到完整 Controller
观点和 Solver 答案，角色独立不代表错误来源独立。

### 8.2 原子命题覆盖以数量代替对应关系

ID 22：

- Controller 的 A/B/C/D 各有 2/2/2/3 条；
- 修订后 Solver 各只有 1/1/1/1 条；
- Solver 将条件和结论写成同一句；
- 模型 Verifier 接受；
- 代码因数量不足拒绝，返回 partial；
- 最终答案 D 与原标签一致。

`decision.py:75-87` 只用 claim 数量、唯一 ID 和选项前缀检查覆盖，
没有稳定的 Controller claim ID 到 Solver assessment 的对应。
两种不同的拆分粒度会反复冲突；仅比较数量也不能证明真正覆盖了全部命题。

应先建立明确的 claim 对应契约，并区分条件、事实、结论和依赖关系，
尤其不能把“如果 P 则 Q”机械视为“P 与 Q 都必须独立为真”。

## 9. 唯一标签不一致题存在法源冲突

ID 13 的内容：网络购物产品质量纠纷，甲公司同意线上开庭、吴某拒绝；
选项 C 是法院可安排甲公司线上、吴某线下参与，标签给 D，模型选择 C。

核查最高人民法院公布的正式《人民法院在线诉讼规则》，法释〔2021〕12号，
自 2021 年 8 月 1 日起施行：

- 第四条第三项明确允许“同意方当事人线上、不同意方当事人线下”。
- 第二十一条第一项的排除条件为“各方当事人均明确表示不同意，
  或者一方当事人表示不同意且有正当理由”。
- 本题未给出正当理由、不具备技术条件等排除事实。

来源：[最高人民法院正式全文](https://www.court.gov.cn/zixun/xiangqing/309551.html)。

因此按该法源，C 有直接支持，D 的绝对禁止结论有明显疑点。
需要独立复核原题年代、参考法源和标签，不能仅因与标签不一致就断言
“模型答错且 Verifier 错放”。此前仅凭标签作出的这一说法应收回。

原标签和本次 7/30 分数保持不变，不事后替换标签。标签审计须独立记录，
经确认后发布新的数据版本，再报告新版本结果。

## 10. 为什么离线测试通过仍大量失败

专项测试以 FakeRoleModel 为主，通常直接返回预写好的 JSON，
每次使用量固定为 15 tokens，不模拟真实生成延迟或完整 SDK response envelope。

测试确实验证了约束会拒绝不合法输出，但不能证明供应商会稳定产生合法输出。
现有覆盖没有充分组合测试：

- schema 重试与业务修订同时发生；
- content=null、reasoning-only、finish_reason=length；
- SDK 内部 HTTP 重试与题级预算；
- 进行中请求跨越题级 deadline；
- 案情里的否定词与最后提问方向不同；
- 多日期背景与假设时间冲突；
- Controller 带倾向的自然语言通过字段白名单；
- 条件命题拆分粒度与 Solver 合并表达之间的冲突。

此前 232 项测试通过证明了已覆盖路径的行为，不证明生产可用率。
一次 smoke 成功只证明有一条成功路径，称其“完全跑通”过于乐观。

## 11. 观测缺口

批量 CLI 使用 `run_legal_request()`。该入口只返回 LegalMCQRunResult，
在 `runner.py:181` 丢弃题级 Trace、Budget 和 role configs。

失败时 CLI 只存 question_id、error_type、message、failed_agent 和 latency。
BudgetExceededError 的阶段、usage、trace 位于 `diagnostics`，
而 CLI 只读取 `details`，因此 8 个预算失败的 failed_agent 均为空。

结果没有逐调用响应、结束原因、实际模型、重试事件、usage 和 request ID。
因此无法：

- 精确区分本批次各个 schema error 是截断、空正文还是错误字段；
- 还原预算失败之前的候选与修订顺序；
- 计算实际 token 和账单；
- 判断 3 并发是否引发了供应商排队或限流；
- 证明所有失败都来自 LongCat 或全部来自隐藏推理。

这些是必须补齐的诊断信息，不应使用猜测填补。

## 12. 修复优先级与验证方法

| 优先级 | 工作 | 验收方式 |
|---|---|---|
| P0 | 保留 finish_reason、content 状态、usage、request ID、逐调用预算与错误阶段；必要时脱敏保存正文 | 失败题也能还原完整调用顺序 |
| P0 | 只从实际提问判断极性；明确假设日期优先级 | ID 5/12/25 为正向，ID 20 不再绑定 1997 年 |
| P0 | 修复 content=null 的响应适配，不把消息外壳当答案 | 合成空正文得到明确 EMPTY_CONTENT/TRUNCATED 类别 |
| P0 | 将网络重试与题级 deadline 纳入统一调度，并为最终核验预留预算 | 一次重试加一次修订不会无预案地丢弃全部结果 |
| P1 | 缩短角色协议和重复解释，按供应商能力启用结构化输出；适配 reasoning 输出预算 | 先小批独立 dev 验证，记录截断率与 schema 成功率 |
| P1 | 稳定 claim ID 和依赖关系，避免 Controller 结论性引导 | 条件命题不会因不同拆分粒度触发无效修订 |
| P1 | 独立审计标签与法律时点 | ID 13 的法源冲突有明确复核记录，原结果不被覆盖 |
| P2 | 用真实失败响应的脱敏回放和 MockTransport 扩展测试 | 覆盖真实 SDK 形态及组合失败，而不只是理想 JSON |

无需立刻换更贵的模型，也不应继续盲目加大总 token 上限。
先修复可确定的工程问题，再固定新版本与预算，在独立 dev 小样本上验证。
本次 30 题可用于问题复现，不能一边根据结果调参，一边继续宣称其为独立
效果验证集；正式实验仍应使用独立测试集和固定种子 42、43、44。

## 13. 总体判断

失败由多层因素叠加，主导现象是协议不可用率过高，并非已经证明法律能力低下。
输出长度和隐藏推理是合理假设，但缺失元数据使其尚未成为本批次的确定归因。
确定存在的是响应适配、预算调度、deadline、题干极性和日期解析缺陷，
以及原子命题契约和标签质量风险。

推荐顺序：观测补齐、输入解析、输出适配、预算调度、协议收敛，再做模型比较。
